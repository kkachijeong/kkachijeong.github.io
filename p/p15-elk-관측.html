Orca Lake 클러스터 로그 수집과 신규 IDC 수집 전환

표준 없이 흩어져 있던 Orca Lake 클러스터 로그를 서비스별로 검색하고 알림받게 만든 수집 체계

기간
2026
역할
단독 (ILM 정책, Vector 규칙, 사내 ELK 운영은 인프라팀)
  • Filebeat
  • Kafka
  • Logstash
  • OpenSearch(파일럿)
  • Elasticsearch
  • Kibana
  • VVector
  • Docker

무엇을

Orca Lake 클러스터에서 Ambari가 관리하는 서비스와 따로 설치한 Ranger·Trino·Docker 등의 로그를 Filebeat → Kafka → Elasticsearch로 모았습니다. 2026년 가을에는 신규 IDC 서버군으로 같은 수집을 넓혔습니다.

왜

Ambari 내부 서비스와 따로 설치한 서비스의 로그를 같은 기준으로 검색하거나 감시할 방법이 없었습니다.

어떻게

  • 표준 없이 흩어진 클러스터 로그를 Filebeat → Kafka → Elasticsearch로 수집, 서비스별 검색과 ERROR 폭증·수집 중단 알림 구성
    • 자체 파일럿(Filebeat → Kafka → Logstash → OpenSearch)에서 Kafka Connect 커넥터가 OpenSearch와 호환되지 않아 Logstash로 교체
    • 운영 부담을 줄이려고 인프라팀이 운영하는 사내 ELK로 이관, 서비스별 데이터스트림·ingest pipeline·인덱스 템플릿으로 재구성
    • 서비스별로 흩어져 쓰기 불편하던 상세 대시보드를 클러스터 개요와 감사 2개로 정리
  • 신규 IDC 이전 시 수집 설정을 되돌리는 대신 ES 파이프라인을 맞춰 기존 이름 유지
    • 새 배포 구조는 서비스와 컴포넌트를 나눠 보내는데, 기존 ingest pipeline 58개와 템플릿은 합친 이름 기준
    • 두 필드를 결합하면 입력 33종 중 23종이 기존 이름 그대로라 이름 변경 6종과 신규 4종만 대응
    • 데이터스트림 이름을 정하는 주체를 Filebeat, ingest pipeline, 인덱스 템플릿 순으로 배제한 뒤 인프라팀 확인으로 Kafka와 ES 사이의 Vector임을 특정, 명명 규칙 변경은 요청 당일 적용
    • API 키 권한을 조회해 템플릿·파이프라인은 본인, ILM 정책과 Vector 규칙은 인프라팀으로 작업 경계 확정
  • 특정 서비스 로그 누락 추적으로 2자리 연도 날짜 파싱 실패 → ES 문서 거부로 조용히 유실되던 버그 발견
  • 수집량은 근거가 있는 것만 제외: JupyterHub 로그의 약 95%가 헬스체크·프록시 점검 DEBUG라 그 3종만 제외, 근거가 부족한 HDFS 감사 로그와 블록 삭제 로그는 남기고 추이 관찰

결과

  • Orca Lake 10여 대 전 노드의 로그를 서비스별로 검색하고, ERROR 폭증과 수집 중단을 알림으로 받는 상태
  • 신규 IDC 서버군 수집은 기존 이름을 유지하는 쪽으로 전환, 오래 걸리던 순차 배포에 병렬 잡 추가(8대 시험 배포 완료)
  • 남은 일: 명명 규칙을 바꾸면서 구 설정으로 보내던 Orca Lake 쪽에 접두어가 겹친 스트림 22개(천만 건 규모)가 생겨, 30일 보존 기간 동안 파싱되지 않는 손실을 기록으로 남김. Orca Lake 전환은 템플릿 생성 스크립트까지만 준비
